# R3 复核器超时、中断与恢复

2026-11-11，本轮处理上次审查的 N2：外层 `sudo` 被终止后客户端可能继续运行，且旧实现只看删除命令返回值，没有删除后查询、信号处理和强制终止后的原任务恢复。普通本机合成子进程的心跳复现了“父进程超时，后代仍短暂存活”；首次使用 ps 的诊断被沙箱阻止，未计入成功证据。

## 执行与清理

`scripts/reviewer_snapshot.py` 现在先创建容器，记录 CID 和任务标签，再按该 CID 启动。任务标签绑定随机任务号、快照和输入摘要；清理前同时核对名称、CID、镜像和标签。查到其他对象或身份不符时保持未确认，不按名称前缀批量删除。

Docker 客户端通过 VM 内已有的 GNU `timeout` 运行，限时后先 TERM，再按期限 KILL；不依赖只杀掉外层 sudo。启动、查询及删除均有期限。SIGINT/SIGTERM/SIGHUP/SIGQUIT 在控制器中设置中断标志，等待路径向当前客户端转发终止请求，之后仍完成有界清理。实际容器由 Docker API 按精确 CID 清理。容器 PID 1 还有独立的同文件 Python 期限控制器，控制器异常退出后也能终止分析进程；停止后的容器对象仍须 recover 删除。该期限代码包含在启动器摘要中。

删除命令成功不足以确认清理。控制器再次查询 CID、名称，以及仍引用本任务配置路径的进程（不依赖可执行文件名称）。只有创建结果已解决、对象均不存在、客户端已结束且没有清理错误，才确认资源清理。创建结果未知而暂时查不到容器时仍保持 `cleanup-unconfirmed`；以后只查询同一个任务，不自动重新创建。若原记录保留 create 成功事件和已落盘的 CID stdout，可恢复创建已完成这一事实；只有错误码或暂时查不到对象不算证明。明确失败但缺少证明的任务仍可能长期未确认，未增加自动放弃或删副本动作。

## 记录与恢复

默认记录位于 VM 的 `~/.cache/harness-review-attempts/review-<任务号>/`。目录为 0700，记录和日志为 0600；只读挂载进容器的 stage 与日志、CID 文件、Docker 配置及任务记录分开。成功时删除 stage，保留记录和日志。客户端 stdout 最多保存 2 MiB、stderr 最多 64 KiB；超量时停止该客户端、排空并丢弃超额数据，再按 CID 清理。单个记录只保留最近 128 条客户端事件及单独的创建摘要，累计计数与压缩标志保留。失败时保留 stage 供核对；恢复确认资源清理后才删除这份自建副本。

记录路径固定；移动目录后拒绝自动恢复。操作锁覆盖执行和恢复，进程退出会释放锁。恢复在取得锁后重新读取记录，避免旧状态覆盖并发完成。SIGKILL 无法执行 Python finally；控制器退出后，用原记录恢复资源，不重新 create/start，也不据此生成完成回执。

状态与原始结果在同一份 JSON 中原子提交。完成提交前已观察到的中断不发布完成结果。提交响应未知时，不把原记录覆盖成失败：先查原记录，可能读到已提交结果，也可能只需清理未完成任务。`status` 校验已提交结果的摘要并返回原结果，不重做分析。

| 记录状态 | 含义与下一步 |
| --- | --- |
| prepared / creating / waiting / cleaning | 最近保存的阶段；status 不证明进程当前仍活动 |
| completed | 已提交原始结果；status 返回同一结果，未重新执行 |
| timed-out / interrupted / failed | 无完成结果，保留原失败原因和清理信息；按原任务恢复 |
| cleanup-unconfirmed | 创建或清理仍不确定；保留目录，查询/恢复同一任务 |
| recovering | 最近记录为恢复中；不能据此推断当前进程仍在运行 |
| recovered | 原任务资源已核对清理；不是新完成的复核 |
| completion-unconfirmed（调用返回） | 提交回执未知；先用 status 查询原记录，避免重复分析 |

在 VM 中使用 `python3 -I -B -S scripts/reviewer_snapshot.py status ATTEMPT_DIRECTORY` 或 `recover ATTEMPT_DIRECTORY`。status 只读最近记录，成功读取任何合法状态均返回 0，这不代表任务已完成；recover 只查询和清理原任务。恢复未确认时 CLI 返回 2；提交响应未知返回 3 并提示先查询 status；信号中断返回 128+信号编号，超时返回 124，一般失败返回 1。这些映射有单元测试；VM 故障控制直接调用 API，退出码 1 不代表 CLI 映射的实测。对已完成记录恢复不会重新执行检查或生成新回执。

仍信任 VM 的 Docker、GNU timeout、sudo、宿主 Python、文件系统和内核。本轮未验收断电、内核故障或 Docker 永久不可用；这种情况可能保留未确认任务。进程匹配是本地只读核对，不是独立系统安全审计。记录/日志的保留策略、逐命中映射、运行 nonce、语义近重复、CWE 适用性及独立样本准入仍待处理。R3 未放行。

进入有任务记录的保护范围后，保存或 stage 校验失败仍尝试有界清理，并返回原任务目录及原始失败。记录建立前的 stage 写入或首次保存失败可能留下无可读记录的私有目录；此时不能依赖 status/recover 结清。最终记录保存失败可能只在返回 JSON 中标记 lastJournalSaveFailed，退出码不一定为 2，磁盘也可能仍停在旧阶段。诊断探测在存储异常时可用有界内存收集，不能因此发布完成结果。

VM 内现有 Docker socket 和 sudo timeout 属于既有 root 权限边界；本轮不新增 sudoers，也不扩大宿主 Mac 权限。

启动器字节发生改变，新验收需重新创建快照和质量冻结。原始结果回执仍为版本 2，质量报告仍为版本 6。
