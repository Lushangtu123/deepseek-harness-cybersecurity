## Remaining actionable items

**R1 (Medium): the execution receipt is an echo of the input, not a measurement.**
- `runScanner` returns `...(ruleProfile?{ruleProfile}:{})`, which is the same object the child passed in. WORKBENCH:421 then checks `validDeepSemgrepProfile(result.ruleProfile)`, so it compares the package constant with itself.
- The real guarantee is structural: `return` is only reachable after `stageSemgrepRules` has hash-verified the bytes and `selectSemgrepManifest` has accepted them. The receipt adds nothing beyond "the runner returned normally".
- `coverageKey` is also unbound. A runner returning a valid profile with a forged or legacy `coverageKey` would persist the 17-rule label. The receipt tests only forge the profile, never the key with a valid profile.
- Fix:
  - Have `stageSemgrepRules` return `{file, sha256: hash(raw), count}` using the `raw` it actually wrote.
  - Have `runScanner` return `executedRules:{sha256,count}`.
  - At :421, require `executedRules.sha256===ruleProfile.rulesSha256 && count===17`.
  - Optionally, require `coverageKey` to match `/^[a-f0-9]{64}$/`.
  - Add a test with a valid `ruleProfile`, `executedRules.sha256` set to the base SHA, and expect failure.

**R2 (Medium, test gap carried over): no golden `coverageKey` test.**
- The closure of R5 rests on the claim that "coverageKey derives from the selected manifest". Every dispatch test injects `coverageKey:'selected17'` or `'forged'`, so `buildScanPlan` is never exercised.
- Add a test through `buildScanPlan` or `runScanner` with a stubbed Docker:
  - The legacy semgrep key equals the pre-change value.
  - The deep key differs from the legacy key.
  - The deep key changes if `rulesSha256` changes.

**R3 (Low): language inheritance is only checked against the allowlist.**
- `details.runtime.rules` keeps the base `languages`, and the test only asserts that the 17th rule's languages are in `{python,javascript,typescript}`.
- If the base set were `{python,javascript}` and rule 17 added `typescript`, the inherited `languages` would be wrong and the test would still pass.
- Assert `languagesOf(bundle) deepEqual languagesOf(base)`. Alternatively, derive `languages` from the bundle at :421.

**R4 (Low): bundle ID validation is weaker than the base check.**
- `readDeepSemgrepBundle` checks `typeof r.id==='string'` but not the base pattern `/^[A-Za-z0-9][A-Za-z0-9._-]{0,239}$/`.
- The current bundle is hash-pinned, so this is not live. It matters the next time the profile is bumped. Reuse the same validator.

**R5 (Low): confirmed metadata overwrites base identity fields.**
- At :421, `version:ruleProfile.id` replaces the manifest `rulesVersion` with `'deep-namespace17'`.
- The verified base SHA and count only survive indirectly, through `ruleProfile.baseRulesSha256`.
- Keep the base explicit, e.g. `details.runtime.baseRules = runtime.rules`, before overwriting.
- Also, a failed deep run persists `runtime.rules.count:16` plus `requestedRuleProfile`. Confirm the client labels these runs from `requestedRuleProfile` or `ruleProfile`, not from `rules.count`. Otherwise a failed deep run displays as "16 条".

**R6 (Low): no child-side readiness re-check at :409.**
- The child re-reads `toolStatus({force:true})` but only checks `runtime.ready`. It does not check `runtime.deepRules?.ready===true`, or that `runtime.rules?.sha256===ruleProfile.baseRulesSha256`.
- If the bundle changes after the parent accepts the task, the failure only surfaces at `stageSemgrepRules`, after the snapshot path has been handed to the runner. This still fails closed.
- Adding both checks at :409 is a cheap way to fail earlier.

**R7 (Low, test gaps):**
- Readiness should report `deepRules.ready===false` while `semgrep.ready===true` when `images.json` `rulesSha256` is not the profile base.
- Readiness should report `deepRules.ready===false` when the semgrep image is missing.
- Legacy runs do not reject a stray `result.ruleProfile`. It is harmless today because it is never persisted, but an assertion would keep it that way.
