# Review: mode-bound deep17 Semgrep candidate

Overall, the main path holds up. The selected profile is checked against the package constant at four points: contract hash, `checkWorkspace`, child (`:409`), and runner (`selectSemgrepManifest`). Base bytes are re-hashed at staging time, the 17-rule bundle is pinned by a constant SHA, and the staged copy is `O_EXCL` with mode `0o400`. `coverageKey` comes from the selected `manifest.rulesSha256`. When neither mode nor profile is passed, the legacy path is byte-identical. Ordinary mode is blocked at the contract, and `selectSemgrepManifest` blocks it again. I found no route that silently runs the 16-rule baseline under a deep contract.

The issues below are ordered by priority. I could only judge the excerpts shown. `compareScanSnapshots`, `validStepCoverage`, `hash()` and the full client were not visible.

## High

**1. Client `validWorkspaceRules` dereferences a null workspace (backwards compatibility)**
- `validTask` calls `validWorkspaceRules(v.workspace, …)`, and the first line reads `workspace.ruleProfiles`.
- Legacy joint tasks persist `workspace: null`, and the "old joint tasks retain a null mode" test asserts this. As shown, rendering or validating any legacy task throws a TypeError.
- The plan path is exposed the same way when `next.workspace` is absent.
- Fix: start with `if (workspace == null) return true;`, or the equivalent for legacy and no-mode plans. Add a client test with a `workspace: null` task.

**2. The base-rule check in `workspaceDispatchPolicy` fails open and is not mode-gated**
- `runtime.semgrep?.rules?.sha256 !== undefined && …` means that if `rules` is absent or null, semgrep is reported available in deep mode. The real inspector only sets `rules` on success, but this policy is the gate other callers and fixtures rely on. The runner catches the problem later, but only after the task is created and the source snapshot is handed off.
- The check also runs for every mode. Once ordinary R3 opens, ordinary semgrep would be blocked with `deep-rule-base-mismatch`.
- Fix: `tool==='semgrep' && mode==='deep' && runtime.semgrep?.rules?.sha256 !== deepSemgrepProfile().baseRulesSha256`. Update the fixture to provide `rules.sha256` equal to the base, and add an absent-rules test.

**3. Readiness never checks the 17-rule bundle**
- `createRuntimeInspector`, the dispatch policy, and the inspector cache key `identity(root)` all ignore `scripts/semgrep-deep17.json`.
- If the bundle is missing, modified, or unreadable, the plan and contract still advertise deep semgrep. The step then fails at `stageSemgrepRules`, after the snapshot has been created.
- The realpath strictness in `small()` makes this more likely on the VM. `DEEP_RULES_ROOT` must equal its realpath, so a symlinked install path or a `node_modules` link fails closed permanently.
- Fix: add a deep preflight to the policy, e.g. `deep-rule-bundle-unavailable`, that hashes the bundle against `rulesSha256`. Confirm that `scripts/semgrep-deep17.json` is in the package's shipped file list.

**4. The selected identity is recorded before execution and never confirmed afterwards**
- `:412` writes `runtime.rules = {sha256: selected, count: 17}` into `security_run.details` before the runner starts.
- The runner result only exposes a digest `coverageKey`, so the child cannot confirm that the 17-rule bytes were actually staged.
- `:420` accepts any string. The injected test runner returns `'selected17'`, and the child accepts it.
- Today the runner throws rather than falling back, so this is defence in depth rather than a live bypass. Still, the persisted label asserts something nothing verified.
- Fix: have `runScanner` return `rules: {sha256: <hash of staged bytes>}`. In the child, require it to equal `ruleProfile.rulesSha256` (or the base SHA on legacy runs) before persisting findings or the 17-rule label. Optionally, record "selected" at insert and "executed" on completion.

## Medium

**5. Retest and comparison across rule sets**
- With `retestFindingId`, a legacy semgrep start always runs the 16 base rules. If a finding from the 17th rule can ever reach `security_finding` with `status='fixed'`, a retest will report it absent (false "still fixed / resolved").
- Fix: reject a retest when the original run's rule SHA differs from the retest's, or carry the profile into the retest.
- Also verify that `compareScanSnapshots` refuses to diff across different `coverageKey`s. Otherwise, comparing a 17-rule run with a 16-rule run produces spurious new or fixed findings.

**6. The bundle skips the structural validation applied to base rules**
- The inspector checks base rules for unique IDs, the language allowlist `python/javascript/typescript`, and count ≤ 1000. The deep bundle only gets a hash check.
- The test checks `slice(0,16)` equality and `p.ruleCount === 17`, but never that `bundle.rules.length === 17`, that IDs are unique, or that the 17th rule's languages are on the allowlist.
- Related: `details.runtime.rules` keeps the base `languages`. If `semgrepFileCoverage` uses those, `withoutLanguageRule` could be wrong for 17 rules.
- Fix: add these assertions to `deep-rule-profile.test.mjs`. Either derive `languages` from the bundle, or note that they are inherited.

**7. In-flight tasks created under the previous workspace version fail after upgrade**
- `checkWorkspace` rebuilds the contract with `version: 'workspace-dispatch-s1-2'` and `ruleProfiles`, so any persisted deep task from the earlier version that includes semgrep will hash-mismatch and fail.
- This is fail-closed and probably correct. Document it, or drain those tasks before deploying.

## Low / test gaps

- `selectSemgrepManifest(m, 'deep', undefined)` is not in the rejection table. Add it, along with `(m, undefined, p)` and `(m, 'deep', null)`.
- Add golden `coverageKey` tests via `buildScanPlan`:
  - The legacy semgrep key is unchanged from the pre-change value, so existing coverage history stays comparable.
  - The deep key equals a digest that includes the selected SHA and differs from the legacy key.
- `validDeepSemgrepProfile` reads properties after the key check. That is fine for JSON-parsed data, but if it ever receives a non-plain object, compare a `structuredClone` or a JSON round-trip.
- Client label "17 条 · 深度执行点观察": consider also showing `qualification` ("candidate, not R3/quality-qualified"). This keeps the broad rule from being read as vulnerability evidence, in line with the contract-not-proof framing.
- Operational coupling: any change to the VM's base `rules.json` disables deep semgrep until a new profile and bundle ship. This is intended, but it belongs in the release notes.

## Claims I'd hold back on

- These tests use injected runners. They show that contract and option propagation work, not that native Semgrep executed the 17 rules. That needs the pending VM candidate scan.
- Nothing here supports any detection-quality or R3 statement.
