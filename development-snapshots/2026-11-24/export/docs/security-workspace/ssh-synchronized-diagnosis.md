# SSH 同步诊断（2026-11-09，本步骤已复核归档，根因仍开放）

本轮一次同步采集补上了“新失败没有同次 VM 抓包”“源码未在运行期固定”“两端时钟不能直接关联”的缺口。它没有确认底层根因，也没有把历史聊天侧栏首次读取失败归因为同一问题。没有实施生产修复、部署或 GitHub 推送。

## 检查与来源

74 项本地检查、16 个套件通过；原生工具编译启用 -Wall/-Wextra/-Werror。保留编译器、SDK、头文件、源码和二进制摘要及自有回环 socket 的正控制。运行前创建独立只读快照，17 个运行输入按摘要校验；每个 FD 连接器从已校验的同一字节缓冲区执行。已有管理器按固定摘要加载，169 项日常程序基线来自更早、独立的记录。前后核对一致。

QEMULauncher 按当前用户、进程出生时间、监听 FD 和 socket generation 核验；通过它打开的预期 VM 磁盘路径及 inode 元数据绑定到目标实例。不读取磁盘正文，不增加宿主权限。宿主仅只读计数；tcpdump 和 root 读取仅在原隔离 VM 内执行。

VM 确认 tcpdump listening 后发送 READY；宿主观察器就绪，再发 ARM，并收到 ARMED 后启动探针。所有探针与代理退出后发 DONE，VM 回执后继续 5 秒收尾，回收采集子进程并读取同一个 VM 时域的日志。以因果握手及成功连接作为关联正控制，没有相减两端单调钟。

## 观察到的事实

一次运行 96 个合成标记连接，最多 6 并发，direct/fdpass 各 48。84 次收到正确远端标记，12 次未收到。主动关闭发生在成功标记之后的仍计为成功，不以 SSH 退出码 255 判失败。固定 direct 再 fdpass 的顺序有时间混杂，不用两组失败比例判断哪种方式更可靠。

84 次成功都能对应到 VM 内 SYN 与 accepted-key 记录。38 次成功 FD-pass 的宿主端口与 SSH_CONNECTION 端口一致；这是本次正控制，不能证明失败端口也一定保留。

| 无标记结果 | 数量 | 当前证据 |
| --- | --- | --- |
| direct-identification | 2 | SSH 错误词分类，没有记录源端口 |
| connect-error | 1 | 连接器明确在 connect 阶段得到系统 errno 54；未返回连接元数据 |
| connected-and-descriptor-sent | 9 | connect 返回且 SCM_RIGHTS 发送返回 1；仍无远端标记 |

9 次已知端口的失败中，8 次没有同端口的候选 VM SYN，1 次有 SYN、双向 FIN 以及 preauth 日志，没有候选 accepted-key。上述对应依赖“失败端口也被保留”的假设；FD 发送成功不是 OpenSSH 已消费描述符的独立证明。

VM 内共有 86 个不同四元组的初始 SYN，除 84 个成功连接，还有 2 个未归属 SYN 流：一个有入向 RST，一个有双向 FIN 和 preauth，后者与已知失败端口条件性匹配。没有同四元组不同初始序号的复用。因此本轮明确记录 noAdditionalUnassignedGuestIPv4SynObserved=false，不能声称所有失败都发生在 VM 接口之前，也不能借用旧实验的“无额外流”结论。

VM 捕获计数为 344 captured / 344 received / 0 dropped，45,224 字节标志摘要，没有 payload 或 pcap；接口 rx_dropped、rx_errors、rx_missed_errors 前后为 0。sshd 日志 428 行、上限检查未触发，无 MaxStartups/drop 类别，boot 与本轮墙钟/单调钟增量一致。未出现 accepted-key 类别不证明从未认证；原始日志 MESSAGE 和公钥指纹没有传到宿主或模型。

宿主 20 秒内 2,759 个快照，FD 从 220 到峰值 312，最高 FD 编号 311，尾部回到 218。最后探针后仍有 17.543 秒观察；首个 FD 低于或等于初始计数的采样点在最后探针后 10.201 秒。监听队列上限字段为 1，已采快照中 queueLength 与 incompleteQueueLength 都为 0；socketError 无非零值，最大采样间隔 8.86 毫秒。

这些是离散、非原子的监听 socket 快照，不能排除更短瞬态、accept 后错误或其他资源路径。没有读取实际进程 RLIMIT_NOFILE；不能以 launchctl 的 256 或上述峰值解释重置，也没有据此调整上限或队列。

## 收尾和结论

观察器与控制 SSH 已 wait/reap；检查时，本轮 supervisor/tcpdump 原 PID 条目及精确探针标记进程均无残留。检查只代表该时点，不涵盖所有 sshd 会话。日常程序 169 项前后匹配；导出程序 173 项、guest 124 项及整体文件清单核验通过。原始私有样本留在工作目录，只提交源码、差异、合成测试和脱敏汇总供审查。

已完成诊断证据补齐。精确的转发组件和底层原因、历史侧栏首次读取同因关系、普通 R3 独立质量验收及全产品发布保留项继续开放。下一步应先解析 2 个未归属流，并评估同用户权限内的转发端诊断证据；需要变更 VM 网络或其他配置时先给具体可审阅方案。

模型指出 4 项复用缺口，当前只记账，没有改写已经运行的工具：

- 接口接收丢包/错误增量尚未自动纳入 complete 条件；本次两端读取可用且所有增量为 0。
- accepted-key 尚未在原分析器完整分账。事后仅在本机复算 86 条：84 条匹配成功标记四元组，1 条匹配控制 SSH，另 1 条发生在 READY 前 664.359 毫秒、在探针窗口以外。该条具体会话身份仍未知，不能直接声称来自预检。这个补算没有单独交模型审查，也不改变原先冻结的分析器及结果。
- 控制器尚未强制比较预检/后检的 boot、sshd 配置与版本；本次本机逐项比较均相同。
- FD-pass 正控制可增加元数据与 FD_SENT 必备条件；本次 38 个成功正控制均已有这些字段。direct 阶段名称是既有管理器报告标签，同时有 kex_exchange_identification 错误词旁证。
