# SSH 队列诊断候选

候选控制器为每个受管 SSH 请求记录操作类别、排队耗时、是否获得锁、是否调用执行器及请求结果。若等待期间采到活跃的持锁记录，可以用请求引用关联对方的类别和结果。容量采样在新记录中单独标记为 `storage-capacity`。候选提供 `ssh-queue-activity` 只读子命令，活动记录最多 64 条，原有 50 条失败记录使用独立文件。

持锁观察使用单独的文件锁与请求标记。只有在主锁发生竞争且连续两次确认观察锁处于独占状态、两次读取内容一致时，才记下持锁方及采样时间。旧版请求、短暂的锁交接和无法校验的标记会表现为未知。活动文件在释放主锁后尽力写入，保留的字段仅为请求引用、类别、时间、标志和结果。锁忙、文件损坏或写入失败可能造成缺记录，不能把它当作无遗漏的审计日志。

`waitMs` 在取得主锁或退出等待路径时记录。失败样本的 `elapsedMs` 可能包含旧失败日志的写入耗时，活动日志本身也会增加少量本地 I/O。排队超时且执行器未调用，与执行器启动后结果未确认分别记录。持锁引用是采样证据，历史超时的持锁方仍无法追溯。

首版通过 56 项合成回归。复核指出超大整数时间戳会在读取活动文件时溢出。第二版以数字范围校验拒绝超大整数、无穷值、NaN、负数和布尔值，并保留原损坏文件。9 项针对性回归通过，其中 8 项复跑既有活动日志用例，1 项覆盖损坏时间戳。测试使用临时目录、假执行器和自有子进程。现有 SSH 相关回归中的进程退出检查使用受限的 `ps` 读取测试子进程。

两版均先尝试 Claude Opus 5.5 high，额度不足后使用同一审查正文交给 DeepSeek V4.1 Flash high。第一份报告对进入受控验证给出有限通过，并指出了时间戳问题。第二份复核确认该修订。两份报告及回执保存在本机工作目录，审查临时进程和目录已清理。活动记录的设计采用非阻塞建议锁。[Python fcntl 文档](https://docs.python.org/3.13/library/fcntl.html#fcntl.flock) · [Apple flock 手册](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html)

安装版基线与导出版基线已有的容量采样差异在候选中得到保留。当前处于候选验证阶段，后续需在受控环境验收真实采样。手动 Trivy 归档上传和验收中继的直接 SSH 调用仍在本候选的观察范围之外。
