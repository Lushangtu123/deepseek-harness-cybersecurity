# SSH 连接重置定位记录（2026-11-09）

本轮是针对本机隔离 VM 连接的受控诊断，未修改日常程序、SSH 服务配置、UTM 网络或宿主权限。尚未修复底层故障，也未关闭历史侧栏首次读取问题。两轮官方 DeepSeek V4.1 Flash high 复核已完成，限定本次固定快照的诊断归档；两次指定 Claude Opus5.5 high 均因401登录过期未完成。

## 当前结论

96 次固定无害 SSH 命令、最多 6 个并发：84 次收到远端标记，12 次没有标记。每次命令只输出合成标记、任务 UUID、PID、SSH_CONNECTION；一半场景在收到标记后主动断开，41 次标记后的 exit255 属于预期清理，不计为失败。另有 24 次补充采样全部成功，不能合并后宣称故障恢复或推算日常失败率。

48 次使用原生直连，48 次使用 OpenSSH ProxyUseFdpass。后者由固定目标连接器记录本机临时端口后交出已连接 socket，随后由 OpenSSH 直接使用，不引入用户态字节转发。FD传递生命周期、行读取超时/上限、分析边界及元数据口径共17项本地测试通过。两组顺序固定，并非随机对照，不能根据两组失败次数比较 FD 传递的因果影响。

在失败连接中，8 次有准确本机临时端口。VM 的整个 45 秒抓取窗口内，这 8 个端口没有对应报文；39 个成功的 FD 传递连接，其本机端口与远端 SSH_CONNECTION 端口全部一致，且全部有对应 SYN。全部 84 个成功连接均有 SYN。另有 2 个非本轮探针拥有的 SYN，保留为未归属连接，不强行分配给失败探针。剩余 4 个失败没有准确本机端口，不能逐条定位。

抓取位于 VM 内的 any 接口，仅输出 SSH TCP SYN/FIN/RST 摘要，没有 payload 输出、pcap 文件或宿主抓包；344 条报文，内核丢包计数 0。捕获开始/结束的墙钟与单调时钟时长均约 45.062 秒，差异不足 1 微秒。端口关联不依赖宿主和 VM 的绝对墙钟直接相等。原始私有探针和报文摘要只留本机，不放进外部复核提示。

严格观察是：在抓取窗口内没有携带这8个失败连接对应端口的VM报文。若转发组件在失败时同样保留源端口，则支持进一步检查宿主连接经转发、到VM TCP接口之前的路径。39个成功连接的端口一致是正控制，但没有独立证明失败时也保留端口；监听端、端口映射、转发实现和主机资源等具体原因仍未知。这是一项连接路径观察，**不是某个 QEMU/libslirp 缺陷的确诊**。

## 复核过的假设

| 假设 | 本轮证据 | 状态 |
| --- | --- | --- |
| SSH 退出码 255 都是故障 | 41 个主动断开的探针已收到正确远端标记；历史 57 个255中仅4条为零响应 | 原统计口径不成立，已纠正 |
| sshd MaxStartups 限流是原因 | 配置为10:30:100；复现窗口435条完整日志未见限流、drop、fork或内存错误；8个已关联失败没有VM接口报文 | 没有证据支持对这8次失败这样归因；未调整阈值 |
| QEMULauncher 持续 FD 泄漏 | 基线218，24次无失败补充采样峰值242，60秒被动观察回落到218 | 不支持持续泄漏判断；未测得实际进程 FD 限额，仍不能判断瞬时耗尽 |
| 宿主转发队列已满 | 当前用户只读 netstat 返回成功但没有匹配行；定向进程日志无匹配错误 | 空结果不足以证明队列为0或没有未记录错误 |
| 旧侧栏首次读取也是同一原因 | 没有捕获该次失败请求的准确链路、端口或启动身份 | 仍未确定；不从本轮复现追认历史原因 |

MaxStartups 的语义仅据 [OpenSSH 官方说明](https://man.openbsd.org/sshd_config#MaxStartups)解释；配置值本身不是触发证据。FD 传递依据 [OpenSSH 官方配置说明](https://man.openbsd.org/ssh_config#ProxyUseFdpass)及 [Python sendmsg](https://docs.python.org/3.13/library/socket.html#socket.socket.sendmsg)。未找到可直接作为本机根因证明的版本匹配证据。

## 日志及时间身份修正

旧记录的宿主绝对时间窗口与滞后的 VM 墙钟不一致，不能以该窗口0条日志排除 sshd；旧相对窗口只取200条且恰好200条，原truncated=false也不足以证明无遗漏。本轮旧窗口重新取1001条、按1000上限核对，实际425条、未截断、无对应限流等标记；历史连接缺少端口和启动身份，仍不能逐条关联。

本轮复现窗口取1001条，实际435条、未截断、acceptedKey=87，其余所查限流、drop、penalty、fork、内存错误、preauth关闭标记均0。这些是窗口聚合，不给未归属连接虚构任务身份。

首次 preflight 有两处诊断元数据错误：configAvailable 误用了后续 journal 返回码；boot SHA 包含 /proc 末尾换行。后续 postcheck 独立记录 configExitCode=0，统一 strip 后核对 capture/postcheck 启动身份。journal 的启动 UUID 还省略了连字符，boot-normalization.py 使用 UUID.hex 补充核对后，同窗口全部日志属于当前启动。初始源码/结果保留原样，没有覆盖成“从未发生错误”。

## 清理与边界

VM SSH 服务 active；捕获 supervisor、tcpdump 和所有收到标记的探针 PID 均不存在，本机未发现本轮拥有的 SSH 子进程。捕获进程本身已 wait，childStopped=true。未收到标记的失败没有远端 PID，清理证明不虚构其远端 PID；命令本身最多固定等待2秒，没有后台任务。

宿主只读定位到127.0.0.1:49223由QEMULauncher PID39674监听，UTM4.6.4(107)，macOS27.2。当前用户的 launchctl maxfiles=256不是QEMULauncher进程限额，不作为耗尽证据。默认沙箱下宿主日志不可读的结果与随后仅针对该进程、当前用户权限的成功只读检查分开保存。不使用宿主 sudo，不更改宿主权限。
