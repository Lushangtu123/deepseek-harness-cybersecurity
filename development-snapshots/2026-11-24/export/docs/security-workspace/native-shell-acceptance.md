## 隔离与替代边界

命名空间探针先证明了：测试进程使用 UID 1000，在临时 DSH_HOME 的写入不出现在外部正式目录；外部目录 inode、凭据摘要和挂载命名空间不变。候选插件以只读绑定出现在既有固定安装路径，状态和 Unix 套接字均指向临时目录。最终 157 项正式程序、凭据文件与扫描器清单摘要与本轮基线一致。

原生联合预设及其工具限制仍在执行，另外增加了测试专用只读工具围栏和后台范围检查，防止验收启动新任务或切换到其他项目。后台使用候选 RPC、存储与执行库，但由测试启动器激活；没有执行正式启动脚本中针对整个 VM 扫描容器命名空间的重启清理。因此本轮不覆盖正式 systemd 部署、启动/取消、审批拒绝或服务故障恢复，不证明单靠产品边界可以达到测试围栏的限制。

只复用了 VM 已有 DeepSeek API 配置，没有复制其他账号、日常聊天或项目数据库。正式 Harness 实例继续运行，未扩大 Mac 权限或改变 VM 网络隔离。此临时挂载环境用于保护验收数据，不作为新增扫描沙箱能力的交付。

## 失败与恢复记录

首次本机打包将插件图片按 UTF-8 读取，准备阶段即失败，尚未创建 VM 测试环境。改为保留二进制字节后完成准备。

第一轮原生会话记录了 redteam_session_bind，随后以“Cannot read properties of undefined (reading 'prepare')”失败；没有进入测试执行围栏，也没有审查后台请求。检查发现临时 profile 指向 improved 依赖树，启动入口则来自 original-capabilities，工具模块的解析路径和摘要均不同。将临时 profile 与插件依赖统一到启动运行时后，新会话完成上述 6 次调用。依据这组对照，异常判断为测试依赖组合问题；原轮未留下可用调用堆栈，未声称精确定位到某个内部语句，正式运行时没有被替换。

既有 SSH 服务拒绝端口转发，本轮通过 SSH 命令通道转送原生 HTTP/事件流，没有修改 sshd 或网络配置。首次转送器因首行缓冲而等待，修复的是测试转送器。

原生全面浏览曾显示 style-error；Chrome 控制台保留 vendor CSS、manifest 和一次 /redteam/api 的 ERR_EMPTY_RESPONSE。限制临时转送并发为 3 个后，一次新加载未再观察到这类空响应；仍出现测试环境缺少宿主包装入口 /__harness/capabilities 的 404。原空响应没有保留每连接 SSH 退出记录，其具体原因尚未完全定位，不能把后续一次成功视为长期稳定性证明，也不能据此回填此前的加载故障根因。临时环境未取得持久启动诊断日志，资源故障证据来自本轮浏览器观察。

## 本轮结论与下一边界

本轮完成**临时隔离环境中的原生联合审查只读链路、候选审计页展示与报告下载**。模型只读两页，未审阅全部 47 条结果；没有开展漏洞核实。此前 API 模型自述调用数错误的记录继续保留，计数仍以原生执行事件为准。

候选源码仍为 160 项，正式部署保持 .11 的 157 项。本轮未改产品代码、提交或推送。v1.3 普通/深度工作区的执行集成、效果校准、发布者准入缺口和正式部署验收继续按实施进度推进；本轮没有把原型或现有安全审计页标为整套新工作区已交付。
